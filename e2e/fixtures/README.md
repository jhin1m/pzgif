# Benchmark and E2E fixtures

Generated by `node scripts/make-fixtures.mjs`, committed, and **stable by name**.
Phase 1 measures against these; Phase 11 asserts against the same files. Renaming
one silently decouples a benchmark number from the test that was supposed to
protect it.

Everything is synthesised from ffmpeg's own sources — no third-party media, so no
licence attaches to the corpus.

`manifest.json` records each file's size and the reason it exists; the generator
script is the authority on how each is built.

## What each one is for

| File | Spec | Exercises |
|---|---|---|
| `screen-720p-10s.mp4` | H.264, 1280×720, 30 fps, 10 s | G2 desktop throughput — the headline case |
| `phone-1080p-5s.mov` | HEVC in MOV, 1920×1080, 5 s | HEVC decode; the 8.29 MB/frame memory ceiling |
| `clip-vp9-5s.webm` | VP9 in WebM, 1280×720, 5 s | The non-MP4 demux path |
| `portrait-rotated.mp4` | 1920×1080 coded + 90° display matrix | G7 container rotation |
| `loop-small.gif` | 480×270, 48 frames, 20 fps | The canonical compressor example; G3 mobile survival |
| `loop-large.gif` | 800×600, 200 frames | G1 deadlock stress; G4 memory ceiling |
| `photo-grain.gif` | 560×315, 45 frames, photographic + heavy grain | G6 worst case for palette quality |
| `flat-art.gif` | 560×315, 36 frames, 32 colours | G6 best case; validates the "32 colours" copy |
| `odd-dims.gif` | **499×281**, 30 frames | The even-dimension guard GIF→MP4 depends on |
| `anim.webp` | 480×270, 48 frames, lossy | Gates the `webp-to-gif` tool |

## Verifying a regenerated corpus

Dimensions and frame counts are load-bearing and two of them were wrong on the
first generation pass. After any change to the generator, check them:

```bash
cd e2e/fixtures
for f in *.gif; do
  printf '%s: ' "$f"
  ffprobe -v error -select_streams v -count_frames \
    -show_entries stream=width,height,nb_read_frames -of csv=p=0 "$f"
done
ffprobe -v error -select_streams v -show_entries stream_side_data=rotation \
  -of csv=p=0 portrait-rotated.mp4      # must print 90
```

Expected: `odd-dims.gif` is **499,281** — not 498,280. `flat-art.gif` and
`photo-grain.gif` are both **560,315** — odd height, on purpose.

## Two traps that already bit this corpus once

- **`testsrc2` rounds its size to even on both axes.** Asking for 499×281 yields
  498×280 with no warning, which quietly neuters the one fixture whose entire job
  is to be odd-sized. Odd targets are generated one pixel larger and cropped.
- **`crop` aligns to the chroma grid on yuv420p input**, so it rounds an odd
  request back to even too. It has to run *after* `format=rgb24`.

## Deviation from the phase-01 spec

`loop-small.gif` is specified there as "~2.4 MB" and is **~4.0 MB**. GIF size is
dominated by content, not by dimensions, and the frame count, dimensions and
frame rate — the properties every memory and throughput calculation actually
reads — are exactly as specified. Reaching 2.4 MB would have meant removing the
temporal grain, which drops it to ~0.5 MB: a fixture with almost nothing left to
compress, and a poor stand-in for the uploaded GIF the compressor page exists to
serve. The larger file is the more honest input. No gate reads this byte count.
