# Client-Side WASM Media Processing — Feasibility Research (2026)

## 1. ffmpeg.wasm status

- Repo: [ffmpegwasm/ffmpeg.wasm](https://github.com/ffmpegwasm/ffmpeg.wasm) — labeled **"experimental" stability**, "Maintained? yes", 700+ commits. Actively maintained but not "production-hardened" per own badge.
- `@ffmpeg/core` (single-thread) install size ~64.7MB unpacked npm; actual `.wasm` payload commonly cited ~25-30MB gzip varies by build; `@ffmpeg/core-mt` (multithread) ~65.7MB unpacked. Real network transfer is smaller after gzip but still multi-MB — first-load cost is real, must be cached via Service Worker/CDN.
- Perf ([official docs](https://ffmpegwasm.netlify.app/docs/performance/), [issue #326](https://github.com/ffmpegwasm/ffmpeg.wasm/issues/326)): single-thread ~40fps @720p H.264 encode on decent laptop vs native ffmpeg ~500fps (10-15x slower). 1080p ~25fps on MBP2018, 100% CPU all cores, >2GB RAM. Multi-thread (`core-mt`) ~2x single-thread, not near-native — native ffmpeg still 10-50x faster than mt-wasm depending on codec ([dayverse.id](https://dayverse.id/en/articles/why-ffmpeg-wasm-fails-leverage-gpu-acceleration/)).
- Estimate for 10s 720p MP4→GIF (decode+palette+encode, not just raw encode): realistically **5-15s single-thread**, **3-8s multi-thread**, on a modern desktop; 2-4x worse on mid-range mobile. No GPU accel — ffmpeg.wasm cannot use hardware video decode/encode in browser ([dayverse.id](https://dayverse.id/en/articles/why-ffmpeg-wasm-fails-leverage-gpu-acceleration/)).
- Known blockers: no GPU accel; large memory footprint (file copied 2x — page→worker→wasm heap, doubling RAM use, [issue #83](https://github.com/ffmpegwasm/ffmpeg.wasm/issues/83)); iOS Safari OOM crashes reported even on `ffmpeg.load()` ([issue #582](https://github.com/ffmpegwasm/ffmpeg.wasm/issues/582), [issue #745](https://github.com/ffmpegwasm/ffmpeg.wasm/issues/745)); mobile browsers aggressively kill long-running WASM tabs ([dev.to write-up](https://dev.to/javidjamae/ffmpegwasm-vs-a-hosted-ffmpeg-api-where-browser-side-breaks-21k9)).

## 2. SharedArrayBuffer / COEP vs ads — CRITICAL FINDING

- **Confirmed blocker**: Google's own docs state *"The Google Publisher Tag (GPT) does not yet support pages served with [COEP require-corp] restriction"* ([developers.google.com/publisher-tag](https://developers.google.com/publisher-tag/guides/cross-origin-embedder-policy)). Reason: every ad-chain resource (SSPs, DSPs, creatives) would need to opt in via CORP/CORS headers — not realistic across the ad ecosystem. Google's workaround is a **manual "reverse Origin Trial" opt-out** (temporary, per-site, not a real fix) pending Chrome/Google building COEP+ads compatibility — status still unresolved as of this research.
- GA4/GTM mostly survive COEP (they use fetch/XHR, not affected resources) but generic third-party `<script>` tags without CORP headers WILL fail to load under `require-corp` unless `crossorigin="anonymous"` + proper CORS response headers are present — many ad/analytics vendors don't set these ([segmentio/analytics-next#841](https://github.com/segmentio/analytics-next/issues/841), [uper.pl guide](https://uper.pl/en/blog/coop-coep-corp-cross-origin-isolation/)).
- **`COEP: credentialless`**: viable middle ground, doesn't require CORP headers on cross-origin subresources (drops credentials instead of blocking). Support: Chrome yes, Firefox yes (recently shipped), **Safari: NOT supported, no shipping plan** despite WASM threads being enabled ([bugzilla Mozilla](https://bugzilla.mozilla.org/show_bug.cgi?id=1731778), [caniuse](https://caniuse.com/mdn-http_headers_cross-origin-embedder-policy_credentialless), [StackBlitz blog](https://blog.stackblitz.com/posts/bringing-webcontainers-to-all-browsers/)). So credentialless doesn't solve Safari.
- **Recommended real-world pattern** (used by StackBlitz WebContainers, Squoosh, etc.): **isolate the heavy-WASM tool on a separate subdomain/route that IS cross-origin-isolated (COOP+COEP), keep the main marketing/ad-bearing pages NOT isolated.** Two sub-patterns:
  1. Dedicated subdomain (e.g. `tools.example.com`) serving COOP/COEP headers, ads live only on `www.example.com`. Cleanest, no ads on the isolated page at all (ads placed around/outside iframe on parent, or simply no ads on tool page — monetize via Pro upsell there instead).
  2. Cross-origin-isolated **iframe** embedding the tool while parent page is uncontrolled — requires `allow="cross-origin-isolated"` permissions-policy on the iframe; only works if the framed content's own top-level document sets its own COOP/COEP (nested isolation is finicky, and Safari support for nested cross-origin-isolated iframes is inconsistent).
  3. `coi-serviceworker` shim ([gzuidhof/coi-serviceworker](https://github.com/gzuidhof/coi-serviceworker)) — injects COOP/COEP via Service Worker when you can't set real headers (e.g. static hosts). Does NOT solve the ads-vs-COEP conflict — it's a header-injection trick, not compatibility with GPT. Only useful when you accept "no ads on this specific page."
  - Bottom line: **there's no known pattern that gives ads + multithreaded ffmpeg.wasm on the SAME page in 2026.** Every real deployment (Squoosh, StackBlitz, Photopea) either has no ads on the isolated tool surface, or doesn't use SAB/mt at all.
- **Single-thread ffmpeg.wasm needs NO special headers** — no SAB, no COOP/COEP. It's simply ~2x slower than mt (confirmed above), i.e., the "slowdown" is a 2x factor, not 10x. This is the pragmatic default: usable without sacrificing ad monetization.

## 3. Alternatives / recommendation matrix

| Task | Best tool | Why |
|---|---|---|
| Video→GIF frame decode | **WebCodecs API** (native) + `mp4box.js` for demux | Native browser decoder, hardware-accelerated where available, no WASM download, far faster than ffmpeg.wasm decode path. Support: Chrome 94+, Edge 94+, Firefox 130+, **Safari 26.0+ (2026, fully shipped)** — was broken/partial Safari 16.4-18.7 ([testmuai.com](https://www.testmuai.com/web-technologies/webcodecs-safari/)). By 2026 practically all target browsers support it. |
| GIF palette+encode (final output) | **gifski-wasm** ([jamsinclair/gifski-wasm](https://github.com/jamsinclair/gifski-wasm)) | Wraps real `gifski`: pngquant-based palette optimization + temporal dithering = noticeably better quality than gif.js/gifenc. Best-in-class for "make my GIF actually look good," which matters for an ezgif competitor's core value prop. |
| Fast/simple GIF encode, low CPU | `gifenc` or `omggif` | Pure JS, tiny, fast for simple/low-color GIFs, no WASM load cost; quality inferior to gifski. Use for quick-preview mode, not final export. |
| Image resize/format convert (webp/avif/png/jpeg) | **`@jsquash/*`** (resize, webp, avif, png, jpeg) | Actively maintained (releases into 2026), squoosh-derived, modular — load only the codec you need. Good default for image-tool features (thumbnail gen, format conversion). |
| Heavy/complex image ops (crop pipelines, batch resize at scale, filters) | **wasm-vips** | 2-4x slower than native libvips but *faster than native ImageMagick* in benchmarks ([libvips.org](https://www.libvips.org/2020/09/01/libvips-for-webassembly.html)); low memory streaming design (vips's core strength) — best for multi-step pipelines. |
| ImageMagick-specific scripting/filters parity | wasm-imagemagick | Only if you need exact ImageMagick CLI compatibility (`-fx`, specific legacy filters); otherwise slower and heavier than jsquash/vips for equivalent single-step ops. |
| Full video transcoding (format/codec conversion beyond GIF) | ffmpeg.wasm (single-thread default) | Still the only broad-codec-support option client-side; use WebCodecs+gifski for the GIF-specific hot path instead, reserve ffmpeg.wasm for less common format needs or fall back to server (Pro tier). |
| Frame extraction pipeline orchestration | OffscreenCanvas + Web Workers | Keeps decode/resize/palette work off main thread regardless of which codec lib is used; required regardless of stack choice to avoid jank. |

**Recommendation**: For the core GIF-tools MVP, use **WebCodecs (decode) → OffscreenCanvas/Worker (frame ops/resize) → gifski-wasm (encode)** as primary pipeline — avoids ffmpeg.wasm's bundle size, COEP/SAB entanglement, and speed penalty entirely for the single most important flow (video→GIF). Keep ffmpeg.wasm single-thread as a fallback for exotic input formats WebCodecs can't demux (needs `mp4box.js`/`webm` demuxers per-container — coverage gap for less common containers). Use `@jsquash/*` for image-tool features (resize/optimize/format-convert GIF frames, thumbnails).

## 4. Browser limits

- Classic WASM32 memory ceiling: **4GB address space**, but practical safe limit is much lower — Chrome-desktop file-copy pattern in ffmpeg.wasm **doubles memory usage** (input file copied worker→WASM heap), so a "4GB limit" in practice supports far smaller real files, especially combined with browser tab memory caps.
- **Memory64**: stable in Chrome 119+/Firefox 120+, **Safari 18.2+** already shipped; Wasm 3.0 (incl. Memory64) expected across all major browsers by late 2026 ([caniuse](https://caniuse.com/wf-wasm-memory64), [platform.uno state-of-wasm 2025-2026](https://platform.uno/blog/the-state-of-webassembly-2025-2026/)). But even with Memory64, JS-side ArrayBuffer/typed-array practical cap in browsers is ~16GB, and tooling (gifski/ffmpeg builds) needs recompiling with `-mmemory64` — most current WASM builds (incl. ffmpeg.wasm, gifski-wasm) are still 32-bit. Don't rely on Memory64 for MVP.
- **iOS Safari**: real-world reports of OOM crashes on `ffmpeg.load()` alone; recommended safe threshold from practitioner write-ups: **treat >50MB input as "server/Pro tier" territory** on mobile ([dev.to write-up](https://dev.to/javidjamae/ffmpegwasm-vs-a-hosted-ffmpeg-api-where-browser-side-breaks-21k9)); iOS Safari also kills long-running tabs more aggressively (no background WASM execution guarantee).
- **Suggested free-tier limits to advertise**: desktop ~100-150MB / mobile ~30-50MB input video, or cap by duration+resolution (e.g. "up to 60s, up to 1080p") rather than raw bytes — easier to communicate and roughly maps to safe memory envelope.

## 5. UX patterns

- **Progress**: ffmpeg.wasm exposes `ffmpeg.on('progress', ...)`; WebCodecs pipelines must build custom progress via frame-count/total-duration ratio manually.
- **Cancellation**: run ffmpeg/gifski inside a **Web Worker**, terminate the worker to hard-cancel (ffmpeg.wasm has no clean native abort mid-command; worker.terminate() is the pragmatic kill switch).
- **Large files**: use **File System Access API** (`showOpenFilePicker`, streams) where supported (Chrome/Edge) to avoid loading whole file into memory upfront; fall back to `<input type=file>` + chunked `File.slice()`/`ReadableStream` reads elsewhere (no Safari support for FS Access API — need fallback path regardless).
- **Main-thread jank**: mandatory Worker + OffscreenCanvas for all decode/encode/pixel work; never run ffmpeg.wasm or gifski on main thread.

## 6. Risks & honest verdict

- **"100% client-side free tier" is viable functionally but has real UX/monetization tension**: single-thread-only (to preserve ads) means real-world GIF conversion of ~5-15s clips takes single-digit-to-teens of seconds — acceptable for a free tool but noticeably slower than server round-trip for anything longer/larger.
- **Ads + multithread WASM cannot coexist on the same page today** — this is the single biggest architectural risk. Plan MUST pick one of: (a) single-thread only + ads everywhere (recommended for MVP — simplicity, DRY, no infra split), (b) split converter onto ad-free isolated subdomain and monetize that surface via Pro upsell only, ads elsewhere. Given 2-4 week MVP and YAGNI, **(a) is the pragmatic starting point**; revisit (b) later if conversion speed becomes a competitive complaint.
- iOS Safari is the weakest link for both compute (no COEP:credentialless, WASM perf ceiling) and memory (OOM reports) — must gate free-tier limits harder on mobile UA or detect available memory (`navigator.deviceMemory` where available) and steer to Pro/server for large jobs.
- ffmpeg.wasm's own "experimental" self-label plus known OOM/mobile issues (open GitHub issues, no fixed timeline) = moderate abandonment/fragility risk; mitigate by NOT making it the primary GIF pipeline (see §3 recommendation — WebCodecs+gifski avoids most of ffmpeg.wasm's baggage for the core flow).
- Bundle size (~25-65MB uncompressed core) means first-use latency; must lazy-load WASM only when user actually starts a conversion, and cache aggressively (Service Worker) for repeat visits.

## Unresolved questions
- No concrete recent (2026) production case study found of a GIF/video tool site successfully shipping ads + isolated-subdomain WASM split — pattern is inferred from StackBlitz/Squoosh precedent, not confirmed for this exact ad-monetization use case.
- Exact gzip-transferred size of `@ffmpeg/core` single-thread `.wasm` (vs. 64.7MB unpacked) not directly confirmed from a primary source — worth measuring directly before committing to it as default.
- WebCodecs GIF *encoding* (vs decoding) is not standardized — confirmed only ImageDecoder handles animated GIF decode; encode side still needs gifski/gif.js. No native browser GIF encoder exists.
- Real device-tested MP4→GIF benchmark numbers (not extrapolated) not found; the 5-15s estimate in §1 is derived from fps figures, not a direct measurement — recommend a quick internal spike to confirm before finalizing MVP UX copy (e.g. "usually takes 10s").
